# Lab 08 whiteboard reflections

1. **SIGTERM.** The executable marks the app draining, closes the HTTP listener, sends `shutdown`, closes sockets with 1001, stops room timers, and awaits HTTP, WS and replay streams before flushing Pino. Stalled peers are terminated at the configured deadline. A final process deadline exits non-zero on a stuck drain. Exec-form Docker CMD makes Node PID 1 so it receives signals directly; an npm/shell parent can interfere with delivery. Ignoring termination lets the supervisor force-kill players without a close frame.
2. **Stateful scaling.** A room's world and players live in one process. Round-robin instances split that state. Sticky routing by room assigns a consistent owner; Redis pub/sub can relay room events between owners but needs ordering/authority rules and adds latency. We ship one process because it is simple and matches the measured capacity experiment. No multi-instance claim is made.
3. **WSS.** An HTTPS page requires secure socket transport. The provided deployment terminates TLS at Caddy and proxies HTTP/WebSocket traffic privately to Node. The proxy must permit Upgrade and long streams. Server heartbeat ping/pong checks every 15 seconds; public smoke stays connected for 70 seconds. Actual public verification awaits a supplied host/domain.
4. **Origins.** Browser WebSocket connections do not receive fetch's CORS protection. `verifyClient` checks the exact allowlist before a session is allocated. Production missing-Origin connections need an explicit opt-in. Origin is browser cross-site protection, not authentication against scripts that can forge headers. Payload/rate/join/heartbeat/backpressure and IP/room/player limits bound resource use too.
5. **Health.** Liveness asks whether the process responds; readiness asks whether assets exist and the app is accepting work. `/health` remains healthy during drain; `/ready` becomes 503. Supervisors can restart a dead process while deploy controllers withhold traffic from an unready one. Both report the build SHA.
6. **Logs.** Pino writes bounded structured events to stdout with fields such as playerId/roomId, making filtering possible without parsing prose. Platform collection handles retention. Pretty-printing can be done in a separate consumer/transport, following Lab 04's lesson about keeping expensive formatting off the event loop; this app emits raw JSON and does not run a pretty-print transport. Replay files are separate and can contain chat; production does not expose downloads.
7. **Image.** Builder stages need TypeScript, Vite and dev dependencies; the final image needs only Node, production packages, emitted shared/server JS and client assets. Manifest-first layers reuse npm installs after source changes. Node runs as UID 1000 with exec-form CMD. The container smoke measures size and verifies that sources/compiler/tsx are absent.
8. **Capacity and RTT.** Lab 07's loopback lower bound was 128 clients. Lab 08 adds resource-limited Linux container measurements, recorded separately in the report. Neither establishes how many remote European players will have acceptable latency; no real remote RTT is available yet. Repeat on the intended host with real clients before setting the public capacity limit. First investigate tick/RSS/ELU versus transport RTT; raising instance count alone would break shared rooms without ownership/routing changes.
9. **3 a.m. incident.** The intended external health monitor alerts after consecutive failures and reports recovery. It is not configured yet. Start with supervisor exit/restart events and stack-bearing `process.crash` logs, compare `/health` SHA to the release, then inspect rejection counters, RSS, interval ELU and tick p99. Restore the previous image digest if the release caused the outage, then retain evidence for a postmortem.
